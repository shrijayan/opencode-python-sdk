Design doc · implemented

opencode-python-sdk

A maintained, typed Python client for the OpenCode 2.x server API, generated from the upstream OpenAPI spec and kept in sync automatically.

Target: OpenCode 2.1.xSpec: packages/protocol/openapi.json22 Oct 2026
Implemented. This was the original proposal. The shipped design differs in four places; the README is the current reference.
  • The contract is exported from the Effect HttpApi in @opencode/protocol (spec/contract.json), not from openapi.json. That source includes all 96 event schemas and decoded query types, so nothing is scraped from TypeScript.
  • Method names follow the official TypeScript client exactly. Experimental endpoints are not moved under client.experimental; their docstrings say they are experimental. So it is client.session.wait().
  • One Python generator (codegen/, no Jinja2 or datamodel-code-generator) emits models, resources, errors and api.md.
  • Type checking is gated on pyright strict and mypy strict. The minimum pydantic version is 2.12.

Verdict

Worth building. There is no Python client for 2.x today, demand is on record upstream, and the spec is complete enough to generate from. The work that makes or breaks it is the sync pipeline, not the first version of the client.

Build it as a generator plus a thin hand-written layer, so a new OpenCode release becomes a regenerated pull request instead of manual porting. That is exactly what killed the old SDK: it was generated once and then left behind.

What the v2 spec looks like

OpenAPI 3.1, 121 paths, 293 component schemas, all under /api/*. The server also serves it live at /openapi.json. A few properties shape the design:

  • Dotted operation IDs such as session.permission.reply and experimental.session.wait. These map directly onto a resource tree.
  • Success envelopes: most responses are {"data": A}. The TS generator unwraps exact envelopes; we should do the same.
  • Typed errors per status (InvalidRequestError, 401, 404) that map cleanly to exception classes.
  • Two SSE streams: GET /api/event and GET /api/experimental/session/{id}/log, marked with a custom x-effect-stream extension.
  • Nullable everywhere via anyOf [T, null], and unions without OpenAPI discriminators.
Gap: the event payload V2EventEncoded is declared as an opaque JSON string. Event types are not in the spec, so typed events have to come from the TS source (packages/client/src/shared-events.ts) or be requested upstream.

Architecture

Four layers. Only the bottom and top are written by hand; the middle two are regenerated from the spec.

L4
Helpers hand-written

OpencodeServer launcher (spawns opencode serve with a per-boot password and isolated HOME), session.run() (prompt, wait for idle, return transcript), typed event dispatch.

L3
Resources generated

client.session.prompt(...), client.mcp.list(), client.experimental.session.wait(...). Sync and async twins from one template.

L2
Models generated

pydantic models for all 293 schemas, plus error classes per declared error type.

L1
Transport hand-written

Base URL, Basic auth, retries with backoff, timeouts, envelope unwrapping, error mapping, SSE iteration. The only place that touches httpx.

Keeping L1 small and stable means generated code never imports httpx directly. Swapping the transport (for example an in-process test server) touches one file.

Public API

The shape follows the operation IDs, so anyone reading the TS client or the server source can guess the Python name.

from opencode import Opencode, OpencodeServer

with OpencodeServer(cwd="./sandbox", isolated_home=True) as server:
    client = Opencode(base_url=server.url, password=server.password)

    client.wait_until_ready(agent="reviewer")          # agents load async after boot
    session = client.session.create(agent="reviewer", model="anthropic/claude-sonnet-5-5")

    client.session.prompt(session.id, text="Review the diff", files=[...])
    client.experimental.session.wait(session.id)

    for msg in client.session.message.list(session.id):   # auto-paginates
        print(msg.role, msg.text)

# async twin, same names
async with AsyncOpencode(base_url=...) as client:
    async for event in client.event.subscribe():
        match event:
            case SessionIdle(session_id=sid): ...
            case UnknownEvent(): ...                 # new server events never crash old clients

Mapping rules

  • session.permission.reply becomes client.session.permission.reply().
  • Path, query and body fields are flattened into keyword arguments; non-object bodies become one payload= argument. Same rule as httpapi-codegen.
  • {"data": A} is unwrapped to A; no-content returns None.
  • SSE endpoints return an iterator (sync) or async iterator. No silent auto-reconnect; offer it as an opt-in helper.
  • Everything under /api/experimental lives under client.experimental, so users can see what may change.

Staying current with v2

The goal is that a new OpenCode release costs a review, not a rewrite.

  1. Spec sync job. Nightly workflow fetches packages/protocol/openapi.json at the latest release tag, regenerates, and opens a PR with the diff and a changelog of added, removed and changed operations.
  2. Drift check in CI. Generated code is committed; CI regenerates and fails if the tree changes. Upstream uses the same rule for the TS client.
  3. Version mapping. SDK minor tracks the OpenCode minor (SDK 2.1.x targets server 2.1.x). client.server_info() warns once if the server is outside the supported range.
  4. Forward-compatible models. pydantic extra="allow", unknown enum values kept as strings, UnknownEvent for new event types. Old clients keep working against newer servers.
  5. Contract tests. Start a real opencode serve in CI with a stub provider and exercise auth, session create, prompt, wait, paging and interrupt. This catches behaviour changes the spec cannot express.
  6. Generator owns its files. A manifest lists generated files, so regeneration deletes stale ones without touching hand-written code.
  7. Upstream path. Keep the generator spec-driven and dependency-light so it can be proposed upstream under #54300 if maintainers want an official Python client.

Risks

  • Upstream ships its own client. Reduce the cost by commenting on #54300 early and keeping the generator easy to donate.
  • We hold the project's name on PyPI. Users may read opencode as official. The README says it is community-maintained and that the repo and PyPI name will be transferred to OpenCode on request.
  • Event types are not in the spec. Extracting them from TS source is brittle. Ask upstream to publish event schemas in openapi.json.
  • Experimental endpoints churn. wait and session log are experimental, yet the headless flow depends on them. Isolate them under client.experimental and cover them with contract tests.
  • Server side effects. A server started inside a project loads that project's AGENTS.md and skills. The launcher should default to an isolated working directory and HOME.
  • Spec title says "Experimental HttpApi surface". The spec itself may reorganise. The sync job and drift check exist for this.
