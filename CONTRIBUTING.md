# Contributing

Thanks for helping. Most of this client is generated by [Ferrule](https://github.com/shrijayan/ferrule) from
`openapi.json` and `stainless.yml`; the SDK's own features are written by hand next to it.

## Setup

```bash
uv sync
./scripts/mock --daemon   # the mock server the generated tests call (needs Node)
uv run pytest
uv run pytest --confcutdir=tests/custom -o asyncio_mode=strict -o addopts="-ra --strict-markers" -m "not live" tests/custom
```

The generated tests use pytest-asyncio; the hand-written ones in `tests/custom` use anyio and trio, so they run
apart.

Live tests start a real `opencode serve` and need the [OpenCode CLI](https://opencode.ai) on `PATH`. They make no
model calls and use a temporary data directory:

```bash
uv run pytest --confcutdir=tests/custom -o asyncio_mode=strict -o addopts="-ra --strict-markers" -m live tests/custom
```

## Checks

CI runs all of these; run them before opening a pull request.

```bash
uv run ruff check .
uv run ruff format --check .
uv run pyright
uv run mypy
uv run pytest   # and tests/custom, as above
```

## Documentation

The site in `docs/` is built with MkDocs Material and mkdocstrings. The API reference is generated from docstrings
at build time by `docs/hooks/types_reference.py`.

```bash
uv sync --group docs
uv run mkdocs serve
uv run mkdocs build --strict
```

### Docs must keep up with the code

A change to the public API is not done until the docs cover it. `mkdocs build --strict` (docs workflow) fails on a
broken link or cross-reference. Resource and type pages are generated from the code, so a new endpoint appears on
its own; add a row for a new resource group to `docs/guides/index.md`, give a new hand-written export a docstring
and a `::: opencode.Name` directive in `docs/reference/`, and update every guide that mentions renamed or removed
API.

## Layout

| Path | What it is | Edit by hand? |
| --- | --- | --- |
| `codegen/extract/` | Exports the OpenCode contract from `@opencode/protocol` | Yes |
| `spec/contract.json` | The exported contract | No, run the extractor |
| `scripts/opencode/` | Contract to `openapi.json`, and the model names in `stainless.yml` (from Ferrule) | Rarely |
| `openapi.json`, `stainless.yml` | What Ferrule generates from; `stainless.yml` also lists the files Ferrule keeps | `stainless.yml` yes |
| Files listed in `ferrule.lock` | Generated code, tests and runtime | Prefer not; edits are kept by a three-way merge |
| `src/opencode/lib/`, `_events.py`, `_rpc.py`, `_pty.py`, `_server.py`, `_service.py`, `service.py`, `testing.py`, `_errors.py` | This SDK's own features | Yes |
| `tests/custom/` | Tests of the hand-written code | Yes |

## Updating to a new OpenCode version

The `Sync OpenCode spec` workflow does this nightly and opens a pull request that updates `spec/contract.json`,
`openapi.json` and `stainless.yml`. When it is merged, the `sdk` workflow regenerates the SDK with Ferrule and opens
a `ferrule/regenerate` pull request labelled with the semver bump of the public API change. To do it locally:

```bash
cd codegen/extract
bun add --exact --ignore-scripts @opencode/protocol@<version> effect@<matching version>
bun run extract.ts
cd ../..
uv run --no-project --python 3.12 python scripts/opencode/contract_to_openapi.py spec/contract.json openapi.json
uv run --no-project --python 3.12 python scripts/opencode/config_models.py openapi.json stainless.yml
ferrule regenerate --repo . --spec openapi.json --config stainless.yml
```

`ferrule regenerate` commits the new generation on the `generated` branch and merges it into the current branch,
so hand-written code, edits to generated files and the `keep_files` of `stainless.yml` survive. Review the diff of
`api.md`, and update the README version table if the OpenCode minor version changed.

## Changing generated code

Change `stainless.yml` (or the spec conversion) and regenerate, or fix the generator in Ferrule. A small edit to a
generated file is kept by the next regeneration's three-way merge, but a change in `src/opencode/lib/` is clearer.

## Releases

Releases are automatic. Every merge to `main` that changes `src/`, `spec/` or `pyproject.toml` runs CI, picks the
next version from the merged commit subjects, publishes to PyPI and creates a GitHub release with generated notes.
Docs, tests and CI changes alone do not release.

Use [Conventional Commits](https://www.conventionalcommits.org/) subjects; with rebase merging, every commit lands
on `main` as written:

| Subject | Bump |
| --- | --- |
| `fix: handle empty cursor` | patch |
| `feat: add session.run helper` | minor |
| `feat!: rename Opencode.server` or a `BREAKING CHANGE:` footer | major (minor while below 1.0) |
| anything else (`chore:`, `refactor:`, ...) | patch |

The version comes from git tags (`hatch-vcs`); there is no version number to edit. To release without package
changes, run the Release workflow manually with **force**.
